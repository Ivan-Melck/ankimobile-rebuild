# Independent desktop / iOS backend comparison

The reference executes the pinned fork's compiled Python binding, real Qt
reviewer post-answer policy, RWKV coordinator and embedded model backend. Only
window drawing and GUI task dispatch are replaced. The other peer executes
`AnkiCollection`, the same Swift collection path used by the iOS app. Both use
synthetic collection copies generated by the original scheduler.

## Recorded result and cleanup state

On 2026-10-27, all 840 acceptance cases passed: 20,115 preparations, 20,093
answers and 100,553 comparisons. Source `db7314a` subsequently passed 56 core
checks (four optional skips), both server sync tests, vectors, the iOS build
and nine UI tests. See [verification](../../docs/verification.md) and the
[sanitized report](../../docs/evidence/rwkv-differential-2026-10-27.json).

The local test environment was deleted afterward: `Vendor/anki/out`,
`NativeEngine/target`, `.build`, temporary profiles, clock library and local
logs. Source and this harness remain. The commands below deliberately rebuild
those generated files; no prepared environment or private fixture is currently
available. Documentation checks do not recreate it.

## Protecting the installed Anki

Both peers **must** pass a bubblewrap namespace audit before running. Their
home, temporary files, XDG directories and Anki profile are confined to a new
private test directory. The live home directory and user session sockets are
hidden, the host filesystem and repository are read-only, the installed
`/usr/bin/anki` launcher is masked, and network and process namespaces are
separate. An audit verifies an owned read-only sentinel and rejects access to a
host loopback listener. It never attempts to write to a real user file.

There is no fallback to an unisolated process. The reference and Swift driver
also refuse a direct launch without the audit marker. No installed Anki
process is stopped, no real collection is opened, and no credentials are
loaded. This harness intentionally accepts no user collection path.

When rebuilt, the reference has its own `Vendor/anki/out/pyenv` virtual environment;
it is not installed into the user's or system's Anki. Compilation uses normal
developer tool caches. The runtime sandbox exposes only that Python runtime,
read-only source/build products and the writable synthetic test directory.

## Running on Linux

Prerequisites: bubblewrap with user namespaces enabled, C compiler, protoc,
the fork's `just`/uv/Rust prerequisites, and Swift. Build and compare with:

```sh
scripts/compare-fork.sh --output /tmp/anki-rwkv-comparison.json
```

To reproduce the full 840-case acceptance matrix recorded on 2026-10-27:

```sh
scripts/compare-fork.sh --jobs 8 --steps 24 \
  --scenarios standard mixed refresh undo redo reopen rollover \
    fsrs4 fsrs5 fsrs7 dynamic-dr dynamic-dr-fsrs7 dynamic-replay grade-order-off \
  --output /tmp/anki-rwkv-comparison.json
```

The rollover case reopens both copies on the next scheduler day; continuous
midnight UI transitions are a separate acceptance case. Dynamic replay uses
two current presets, without complex historical preset-migration rules.

The default matrix covers five models, four recurrent precisions, Instant,
Curve and both together, and standard, mixed-preset, refresh-cadence,
undo, redo, reopen and rollover fixtures. Additional scenarios cover FSRS
4/5/7, dynamic retention (including active FSRS 7), dynamic preset replay and disabled grade ordering.
Flags such as `--models sm56 --precisions f32 --steps 24` narrow it.
`--jobs` controls parallel independent cases (default four); each has separate
processes, namespaces, profiles and clocks. Both peers use one Rayon thread
per process to avoid oversubscribing the host.
Failed synthetic cases are retained in private temporary directories for
inspection. Passing cases are removed unless `--keep` is supplied.

Observations include selected card, displayed counts, all answer states,
neural heads and intervals, installed candidate scores and queue order,
complete card/note/revlog/grave tables, and hashes
of all recurrent modules. Queries must not mutate reference recurrent state.
The controlled clock changes only wall time in the two children; monotonic
clocks remain real. Action timestamps are whole seconds to avoid Python vs
Foundation fractional-millisecond conversion differences. Measured answer
durations still include fractions of seconds. Float comparisons use absolute
and relative tolerance `1e-5`; integers and strings compare exactly, as do
the hashes of recurrent module bytes.
The report records the GitHub main check, reference revision, executable hash
and matching model hashes. Source changes in the reference are rejected.
`summarize.py INPUT OUTPUT` makes a public report from a completed matrix,
removing temporary paths and retaining each case's isolation audit. It does
not include collections, media or process logs.

After `swift build --build-tests`, a built test executable can also run through
`python3 tools/comparison/isolated_command.py /absolute/path/to/test-executable`.
This uses the same audit and private profile with real wall time. First run
`compare-fork.sh` (a narrowed case is sufficient) to recreate the reference
Python environment and clock library. Then build and run the core suite:

```sh
swift build --build-tests
TASK_TEST_BIN="$(swift build --show-bin-path)"
if [ -x "$TASK_TEST_BIN/FlashcardsCoreTests-test-runner" ]; then
  TASK_TEST_EXECUTABLE="$TASK_TEST_BIN/FlashcardsCoreTests-test-runner"
else
  TASK_TEST_EXECUTABLE="$TASK_TEST_BIN/FlashcardsCorePackageTests.xctest"
fi
python3 tools/comparison/isolated_command.py "$TASK_TEST_EXECUTABLE"
scripts/test-sync.sh
```

The wrapper omits private-fixture environment variables. Its ordinary core run
skips the two optional private tests and two server-dependent tests; the sync
script runs the latter separately with disposable fake accounts.

On Linux, `scripts/test-sync.sh` builds the synthetic server and clients and
then runs them automatically in one audited private network namespace. Its
two fake accounts test ordinary sync/media behavior and RWKV candidate-cache
invalidation after incoming reviews and full collection replacement. It
requires the private reference Python environment created above. The server
is reachable only by its test clients; it cannot reach the host's Anki or
AnkiWeb. Hosted macOS CI uses disposable accounts/profiles on its fresh runner.

The diagnostics are gated by Cargo's `validation-comparison` feature and
are absent from shipping builds. This is a collection/reviewer comparison,
not proof of complete desktop GUI, add-on, sync-service or iOS UI parity.
Known unsupported features remain documented in the main compatibility report.
